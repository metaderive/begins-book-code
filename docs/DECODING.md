# 解読の経緯（How it was reverse-engineered）

このライブラリが実装しているフォーマットを、どうやって公式仕様なしに解読したかの記録。
フォーマットそのものの仕様は [../SPEC.md](../SPEC.md) を参照。

- 手法: サンプルブックの差分解析（1 要素だけ変えた 2 つのコードを比較）
- 検証: 自作エンコーダで生成したコードを実機に読み込ませる往復テスト
- 環境: Nintendo Switch 2 日本版 / Culdcept Begins 日本語版 Ver 1.0.3
- 期間: 2 日 / サンプル 20 本超（すべて手作業で作成）

---

## 0. 準備 — 既存フォーマットを先に学ぶ

本題の前に Hearthstone のデッキコード（deckstring）仕様を調べた。
「整数 ID を varint で詰めて Base64 化」「枚数クラス別にグループ化」「正規順序ソート」
という設計を頭に入れておいたことが、未知フォーマットの解読でずっと比較軸として効いた。
「varint を使っているか」「正規形はあるか」という問いを最初から持てたのが大きい。

## 1. 方法論 — 最小差分ペアを積む

「ブックの内容（カード名＋枚数）」と「生成されたコード」のペアをサンプルとして集める。
**1 要素だけ変えた 2 つのブック**（カード 1 枚入れ替え／Aカード1枚追加）のコードを
バイト列で比較すると、どのバイトが何を表すかが 1 つずつ分かる。この最小差分ペアが
全編を通じて最強の武器になった。

## 2. 文字レイヤー — 記号置換 Base64

コードには `& ? # @` という非 Base64 文字が混じる一方、`I O l 0`（紛らわしい文字）が
一度も出てこない。「置換では？」と当たりをつけ、記号 4 種の割り当てを総当たりで生成し、
「S2 は S1 に数バイト挿入しただけのはず」等の構造制約でスコアリングして特定した。

→ 標準 Base64 の紛らわしい 4 文字を記号に置換したアルファベット（`I→& O→? 0→# l→@`）。
これでコードがバイト列になり、以降の解析が可能になった。

## 3. 骨格の把握 — 差分と集合演算

最小差分ペアをバイト化して並べると構造が見えた。

```
S1: c0904010 | 00    | 07 03 19 00 0c 16 0e 02 0a 4c   ← 基準
S2: c0904010 | 01 00 | 07 03 19 00 ...                 ← Aカード1枚 → 2バイト挿入
S4: c0904010 | 00    | 03 19 00 ... 0b 4c              ← 1種入れ替え → 1バイト差
```

集合演算（S1∖S4 = {07} ↔ 入れ替えたカード）から「1 バイト = カード固有 ID」が確定。
ヘッダー／Aカード数／ID 列という骨格が見えた。

## 4. 一番の敵は「書き写しミス」だった

中盤で最も苦しめられたのは、フォーマットの複雑さではなく**人間の転記ミス**だった。

| 症状 | 真相 |
|---|---|
| 同一デッキなのにコードが 1 箇所食い違う | `AScj` → 正しくは `AScJ`（j / J の取り違え） |
| Aカード0枚なのに謎のバイト | `AwaD` → 正しくは `AwAD`（a / A の取り違え） |
| 確定 ID が本に不在 | サンプルのカード名の取り違え |

記号置換で守られているのは 4 文字だけで、大文字・小文字の混同は防げない。対策として、
確定 ID 表と多重集合で照合する監査スクリプトを用意し、以降は転記ミスを機械的に検出した。

## 5. ブレイクスルー

- **スロット継承**: 40 種 × 1 枚ブックの「1 種入れ替え」シリーズが 1 バイト以外完全一致。
  差分から複数カードの ID が一気に確定した。
- **Aカードデータ**: 「Aカードの位置参照」がリトルエンディアンのビット列に 6bit ずつ
  詰まっていると判明（参照値 × 4 = ID 列上の位置）。予測を外したことが正解の形を教えた。
- **ヘッダー = ページ別ヒストグラム**: 同じ枚数構成なのにヘッダーが違う例から、
  ヘッダーが「ページ別 × 枚数クラス別の種類数」をビット詰めしたものだと判明。
  既知の全ヘッダーをバイト単位で再現できるビット文法に到達した。

## 6. 1 バイト衝突とページ方式

スペル入りのブックで、確定済み ID と同じバイトが別カードに現れた。カードは約 400 種で
1 バイト（256）に収まらないので当然の帰結。**コードの 1 バイトは真 ID の下位バイト**で、
ID 列は `[ページ0][ページ1]` の 2 部構成、境界はヘッダーが与える。
→ 真 ID = バイト値 + 0x100 ×（ページ1 部にいるか）で復元。

Hearthstone が varint で明示的に解いた問題を、このフォーマットは「並び順への暗黙依存」で
済ませている。約 400 ≦ 512 だから成立する割り切りだった。

## 7. 往復テスト — 実機による実証

ヘッダー・Aカード・ID をすべて解読したので、逆にコードを生成するエンコーダを書いた。
既存サンプルに無い構成（20 種 × 2 枚・ページ1 カード入り／枚数混在＋Aカード）の
コードを生成して実機に読み込ませたところ、**意図通りのデッキが復元された**。
20 枚中 1 枚のズレが最後の ID 表バグ（`0x81` フラグ付きAカード参照の誤読）を教えてくれた。
解読の実証であると同時に、実機を使った最強の ID 検証手段でもあった。

## 8. 効いた手法まとめ

1. 最小差分ペア設計（1 要素だけ変えた比較）
2. 順序に依存しない多重集合の差分・共通部分（転記ミス検出にも有効）
3. 機械総当たり＋構造制約スコアリング（アルファベット・ヘッダー解読）
4. 予測 → 実測 → 修正（外れた予測が正解の形を教える）
5. 反証を上位仮説へ昇格（「ヒストグラム説」が壊れた瞬間にページ分割説が生まれた）
6. 常設の監査スクリプトで人間の転記ミスを機械検出
7. 実機往復テストによる最終実証

## 9. Hearthstone 方式との比較

このフォーマットは「デッキ共有コード」として、Hearthstone の deckstring と同じ問題を
解いている。だが解き方が正反対で、そこに設計思想がよく表れている。

### 前提: Hearthstone deckstring の方式
Base64 でエンコードされたバイト列。中身は varint（可変長整数）の列で、
`[予約 0][バージョン][フォーマット]` の後に、カードを **枚数クラス別にグループ化**
（1 枚組・2 枚組・n 枚組）して DBF ID を varint で並べる。各グループ内は
**DBF ID 昇順にソート**され、同じデッキからは常に同じ文字列が出る（正規形）。
仕様は公式が公開している。

### 方式の対応表

| 観点 | Hearthstone deckstring | 本フォーマット（ビギンズ） |
|---|---|---|
| カード ID の表現 | varint（大きい ID は複数バイトに伸ばす） | 下位 1 バイト固定＋ページ判別 |
| ID が 1 バイトを超える問題 | varint で**明示的に**解決（曖昧さゼロ） | 並び順（ページ 0/1 の 2 部構成）で**暗黙に**解決 |
| ID 衝突 | 起きない | 起きる（同一ページ内では 1 対 1、ページで一意化） |
| カード数の上限 | 事実上無限（varint 次第） | 512 種（2 ページ）で頭打ち |
| 枚数の表し方 | 枚数クラス別グループ＋（n 枚組は枚数を varint で明記） | 枚数クラス別グループ（種類数だけをヘッダーにビット詰め） |
| 正規形（同一デッキ→同一文字列） | あり（ID 昇順ソート） | なし（並びに編集履歴が漏れる） |
| 文字エンコード | 素の Base64（機械前提） | 記号置換 Base64（`I O l 0` を回避、手運び前提） |
| バージョン/フォーマット領域 | あり（先頭に明示） | 実質なし（先頭の常時 1 ビットのみ） |
| 仕様の公開 | 公式が公開 | 非公式・リバースエンジニアリング対象 |

### 共通点
- どちらも「整数 ID の列を Base64 系でテキスト化」する同じ発想
- どちらも**枚数クラスでグループ化**する（1 枚・2 枚…をまとめる）——
  カードはほぼ 1〜数枚しか入らない、というカードゲーム共通の性質を突いた圧縮

### そこから読み取れる筋

**同じ問題への正反対の解は、「誰がコードを運ぶ想定か」の違いに行き着く。**

- Hearthstone は **機械が運ぶ**前提で設計されている。クリップボードや API で受け渡し、
  varint で無限の拡張性を確保し、正規形でデッキの同一性判定を可能にし、
  バージョン領域で将来の変更に備え、仕様を公開してサードパーティのエコシステムを育てる。
  「開かれた・拡張可能・機械可読」を最優先した設計。

- 本フォーマットは **人間も運ぶ**ことを許容する前提が透けて見える。紛らわしい文字を記号に
  逃がし、4 文字区切りで表示し、手入力・読み上げ・スクショ転記に耐えようとする。
  その代わり、バイト数を切り詰めるために ID をページ方式で暗黙圧縮し、拡張性
  （512 枚・単一シリーズ・バージョンなし）を割り切り、正規形も持たない。
  「今この用途にギリギリ最適化された・人に優しい」設計。

varint か、ページ方式か。ソートするか、登録順を残すか。バージョン領域を持つか、持たないか。
これらの選択は全部、**「そのコードは最終的に誰の手を通るのか」** という想定の写し鏡に
なっている。フォーマットは、想定ユーザーと制約条件の化石だ。

（なお本フォーマットで varint 説は早い段階で棄却できた——ID 種類数とバイト数が
きっちり一致し、継続ビットの入る余地がなかったため。この「バイト数の勘定」が、
2 つの方式を分ける最初の分岐点だった。）

## 残っている課題

- カード ID 表の拡充（確定 43 種 / 約 400 種）
- Aカード数バイトの `0x80` フラグの意味
- ページ1 部の並び規則の細部（エンコーダ品質向上用）
